## Why this matters

`npm audit` reports 13 vulnerabilities on this repo. Twelve of them are noise
for this deployment, and one line of `package.json` clears nine at once.

The nine Next.js advisories all carry the affected range `>=16.0.0 <16.2.11`.
The pinned version is `16.2.6`. So the fix is a **patch bump inside the pinned
minor line**, not a major upgrade. This is worth stating plainly because
`npm audit fix --force` says otherwise:

```
fix available via `npm audit fix --force`
Will install next@16.3.0, which is outside the stated dependency range
```

That advice is wrong for this repo — it jumps a minor version for no reason.
Do not run `npm audit fix --force`.

**Honest scoping of the actual exposure**, because padding a security finding is
worse than not filing one:

- `git grep -n '"use server"'` over `*.ts`, `*.tsx`, `*.mjs` returns **nothing**.
  This app has no Server Actions, so the Server-Action DoS, Server-Action SSRF,
  unbounded-Server-Action-payload, and unauthenticated-Server-Function-endpoint
  advisories have no reachable surface here.
- `next.config.ts` is an empty config object, so the rewrites-SSRF advisory has
  no configured rewrites to attack.
- The two "cache confusion of response bodies for requests with bodies"
  advisories are the ones with a plausible surface: this app has three POST
  routes (`/api/dashboard/ingest`, `/api/research/report`, `/api/research/chat`),
  two of which spend money against an OpenAI budget.

So: real exposure is small, and the fix is cheap and in-range. That combination
is why this is worth doing and why it sits at P3 rather than P1. The secondary
benefit is signal — with these nine gone, the next `npm audit` someone runs is
readable.

The remaining four advisories (`vite`, `ws`, `launch-editor`, and `sharp`/
`postcss` reached through the build) are **dev-server and build-time only**. The
deployed artifact is a Cloudflare Worker; `worker/index.ts` handles image
optimization through the `env.IMAGES` binding, not through `sharp`. They are out
of scope and recorded as considered-and-rejected in the plans index.

### Step 3: Prove the app still builds and passes

This is the step that matters. `vinext@0.0.50` is a `0.0.x` package sitting on
top of Next's internals, and a patch bump is exactly where that could break.

```bash
npm ci
npm run build >/dev/null 2>&1; echo "build exit=$?"
npm run lint; echo "lint exit=$?"
npm test 2>&1 | tee /tmp/npm-test-after.log | grep -E "^(✔|✖)" ; echo "npm test exit=${PIPESTATUS[0]}"
python -m pytest test_core.py test_cockpit.py research/test_base_rate.py -q
```

**Verify**, in order of importance:

1. `build exit=0` — **unconditional**. The build must succeed. This is the
   single most important check in the plan.
2. `python -m pytest ...` exits 0. Unaffected by a JS dependency, so this is a
   pure regression check.
3. The lint exit code is **identical to the step 1 baseline**, and if non-zero,
   the error list is identical too. A patch bump must not introduce a new lint
   error, and must not silently fix one either.
4. The `✔`/`✖` test list is **identical to the step 1 baseline** — same names,
   same outcomes. Diff the two logs to be sure:

```bash
diff <(grep -E "^(✔|✖)" /tmp/npm-test-before.log) <(grep -E "^(✔|✖)" /tmp/npm-test-after.log) && echo "IDENTICAL"
```

**Verify**: prints `IDENTICAL`. Any difference — in either direction — means the
dependency bump changed behavior and needs explaining, not accepting.

(`npm run typecheck` exists only if plan 02 has landed. If it is defined, run it

## CORRECTION (2026-08-10, after execution) — the audit count does not reach zero

Two statements in the original plan were wrong, and they were **the plan
author's error, not the executor's**. The plan asserted that `npm audit
--omit=dev` would report 0 vulnerabilities afterwards, while its own step 5 said
"if postcss or sharp survive, record the exact output and move on." Those
contradict each other. The measured reality:

| | Before (`16.2.6`) | After (`16.2.11`) |
|---|---|---|
| `npm audit --omit=dev` count | 3 high | **3 high** (unchanged) |
| `next` carries its own `Next.js: ...` advisories | **yes** — SSRF-in-rewrites, image-opt SVG DoS, Server-Function-endpoint disclosure, etc. | **no** |
| `next` listed as `Depends on vulnerable versions of postcss` / `sharp` | yes | yes |
| `postcss <=8.5.22` (4 advisories) | present | present |
| `sharp <0.35.0` | present | present |

The nine Next.js advisories **are** cleared — that is the substance and it was
achieved. The count stays at 3 because npm counts *packages*, and `next` is
still counted as vulnerable-by-dependency through the `postcss` and `sharp` it
bundles. Clearing those would require `next@16.3.0`, which is a minor bump this
plan deliberately refuses (and which `vinext@0.0.50` has not been validated
against).

The verified done criterion is therefore "no Next.js-specific advisory remains",
not "0 vulnerabilities". Corrected above.

**Lesson for future dependency plans in this repo**: state audit expectations as
*which advisories disappear*, never as a total count. Bundled transitive
dependencies keep the count pinned even when the targeted CVEs are gone.

## Maintenance notes

- **The pinning convention is exact versions, no ranges.** Every dependency in
  `package.json` is a bare version string. Keep `--save-exact` on every install
  in this repo, or a future `npm install` will silently widen a pin.
- **`next` and `eslint-config-next` move together.** They share a version line;
  a mismatch produces confusing lint failures rather than an obvious error.
- **`vinext` is the real constraint on Next upgrades here.** It is `0.0.50` and
  it owns `dev`/`build`/`start` plus the Worker entry point. Before any future
  Next **minor** bump (16.3.x and beyond), check what `vinext` supports first —
  the patch bump in this plan is safe precisely because it stays inside 16.2.x.
- **What a reviewer should scrutinize**: `git diff package.json` should be two
  lines. Everything else in the diff is `package-lock.json`, which is generated
  and should not be read line by line — but it *should* be committed.
- **Deliberately deferred**: the `vite`/`ws`/`launch-editor` dev-server
  advisories, and any `postcss`/`sharp` residue. If the deployment model ever
  changes so that the build runs somewhere untrusted, revisit them.
